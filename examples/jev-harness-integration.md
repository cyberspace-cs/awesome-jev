# 🧠 Jev 深度整合 Harness 实战

> 参考 mu-agent 黑客松总冠军方案
> 
> 核心思路：把大模型的"小决定"全部交给 Jev，大模型只专心干活

---

## 🎯 核心理念

**每一轮对话里都藏着几百个小决定，没人认真做。**

- 交给大模型？太贵、太慢、上下文爆
- 交给死规则？太死板、太容易错
- 交给 Jev？0.3 秒一次，便宜，准确

---

## 🏗️ 四大核心整合点

### 1️⃣ Jev 当"裁判"：35 个判定点全交给 Jev

**问题：** 每一轮对话里有几百个小判断，大模型做这些太浪费了。

**方案：** 拆成 35 个判定点，全部并行问 Jev，大模型只拿结果干活。

#### 核心判定点（部分）

| 判定点 | 问 Jev 什么 | 为什么重要 |
|--------|------------|-----------|
| **新任务还是纠正？** | 这句话是新任务，还是在纠正之前的错误？ | 决定要不要重置上下文 |
| **这段输出哪块有用？** | 工具输出的这几段，哪些是真正有用的信息？ | 只留有用的进上下文 |
| **命令对不对？** | 这条命令是不是用户想要的？ | 避免大模型瞎执行 |
| **真的做完了吗？** | 模型说做完了，真的验证过了吗？ | 防止幻觉 |
| **该不该告诉用户？** | 这个中间结果需要让用户知道吗？ | 人话看板用 |
| **该传给哪个子 Agent？** | 这个信息最该传给哪个子 Agent？ | 蜂群协作用 |

---

### 2️⃣ 上下文精简：只放这一步需要的

**问题：** 上下文爆炸，99% 是没用的东西。

**方案：** 每一步都用 Jev 过滤，只留真正需要的。

#### 过滤规则

```
用户输入
  ↓
Jev 判断：这是新任务还是纠正？
  ↓
Jev 判断：历史消息里哪些和当前任务相关？
  ↓
Jev 判断：工具输出里哪几块是有用的？
  ↓
只把相关的 + 有用的 塞进大模型上下文
```

**效果：** 上下文只占 31%，缓存命中 99%

---

### 3️⃣ 人话看板：干活和讲话分给两个模型

**问题：** 模型越来越强，汇报却越来越难懂。

**方案：**
- 干活模型：专心写代码、调工具，不用管汇报好不好懂
- Jev：从干活过程里挑出真正的新消息
- 讲话模型（Claude/GPT）：把新消息翻译成人话给用户看

```
干活模型（DeepSeek V4）
  ↓ 输出一堆技术日志
Jev 筛选：哪些是真正的新消息？
  ↓
讲话模型（Claude Opus）
  ↓ 翻译成正常人能看懂的话
用户看到：人话看板
```

---

### 4️⃣ 蜂群闸门：Jev 当多 Agent 中间的路由器

**问题：** 多 Agent 协作时，信息乱传、重复传、传错人。

**方案：** Jev 当中间闸门：
- 要不要说出来？
- 要不要告诉别人？
- 前后对不对得上？
- 这个信息最该传给谁？

```
子 Agent 1 输出
  ↓
Jev 判断：要不要传？传给谁？
  ↓
子 Agent 2 收到刚好需要的信息
```

## 💻 核心代码例子

### Python SDK 示例

```python
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()

# 每一轮大模型调用前，并行问 Jev 一堆小问题
decisions = client.system_one(
    state={
        "user_input": "帮我看看这个项目怎么跑起来",
        "history": [
            {"role": "user", "content": "这是一个 Python 项目"},
            {"role": "assistant", "content": "好的，我来看看"}
        ],
        "tool_output": "README.md 内容：..."
    },
    questions={
        # 1. 新任务还是纠正？
        "is_new_task": Choice(
            instructions="判断用户这句话的意图",
            criteria={
                "new_task": "开始一个新任务",
                "correction": "纠正之前的错误",
                "follow_up": "继续上一个任务"
            }
        ),
        
        # 2. 工具输出哪块有用？
        "useful_sections": Noul(
            instructions="这段工具输出里，这部分内容对完成当前任务有用吗？"
        ),
        
        # 3. 真的做完了吗？
        "is_done": Score(
            instructions="模型说任务完成了，完成质量如何？",
            criteria=["完全没做完", "做了一半", "基本完成", "完美完成"]
        ),
        
        # 4. 该不该告诉用户？
        "should_report": Noul(
            instructions="这个中间结果需要现在告诉用户吗？"
        ),
        
        # 5. 该传给哪个子 Agent？
        "route_to": Choice(
            instructions="这个信息最该传给哪个子 Agent？",
            criteria={
                "coder": "写代码的 Agent",
                "researcher": "查资料的 Agent",
                "tester": "测试的 Agent",
                "none": "不用传给任何人"
            }
        )
    }
)

# 大模型只拿 Jev 筛选后的结果干活
if decisions.answers["is_new_task"].choice == "new_task":
    # 重置上下文，开始新任务
    pass
elif decisions.answers["is_new_task"].choice == "follow_up":
    # 保留相关历史，继续任务
    pass

print(f"Jev 判断完成，耗时约 0.3 秒")
```

## 🚀 怎么用到你的项目里？

### 第一步：先加 3 个最核心的判定

不要一下加 35 个，先从最痛的 3 个开始：

1. **工具输出过滤**：Jev 判断工具输出哪块有用，只留有用的进上下文
2. **完成度检查**：Jev 判断模型说"做完了"是不是真的做完了
3. **人话翻译**：Jev 挑出真正的新消息，让小模型翻译成人话

### 第二步：逐步加更多判定点

跑顺了之后，再慢慢加：
- 新任务检测
- 蜂群路由
- 重复日志折叠
- 过期结果清理

## 💡 核心启示

**大模型是发动机，Harness 是整台车。**

以前 Harness 全靠死规则和大模型自己判断，现在有了 Jev：
- 小决定交给 Jev（快、便宜、准）
- 大模型只专心干大事（写代码、做推理）
- 上下文精简，成本暴降，体验暴升
